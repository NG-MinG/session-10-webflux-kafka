Bài 01

Giới thiệu Async Service-to-Service Calls & WebFlux

Vì sao các cuộc gọi đồng bộ giữa service trở thành điểm nghẽn, và reactive programming giải quyết vấn đề đó như thế nào.

Bài 01 · Đặt vấn đề

Vấn đề với giao tiếp đồng bộ

  • Thread bị blockThread gọi service khác phải chờ response mới được giải phóng để xử lý request tiếp theo
  • Cascading failureService A chậm → service B chờ → toàn bộ hệ thống treo dây chuyền
  • Khó scaleKhi có hàng nghìn request đồng thời, số thread cần cấp phát tăng vọt
minh họa · chuỗi block
Bài 01 · Khái niệm

Giao tiếp bất đồng bộ là gì?

  • Sender gửi message và không chờ responseGửi xong là tiếp tục xử lý việc khác ngay lập tức
  • Giống như gửi emailGửi đi rồi tiếp tục làm việc khác, không đứng chờ người nhận trả lời
  • Receiver xử lý khi có thểNgười/service nhận chủ động xử lý theo nhịp độ của riêng mình
minh họa · gửi email
Bài 01 · Công cụ

WebFlux là gì?

  • Spring WebFluxFramework reactive của Spring, song song với Spring MVC
  • Non-blocking, event-drivenKhông giữ thread chờ trong lúc I/O đang xử lý
  • Xử lý hàng nghìn request với ít thread hơnMột số ít thread luân phiên phục vụ nhiều request cùng lúc
event loop · ít thread, nhiều request
Bài 01 · Khái niệm cốt lõi

Reactive Programming

  • MonoPublisher phát ra 0 hoặc 1 phần tử
  • FluxPublisher phát ra 0 đến N phần tử
  • BackpressureConsumer là bên kiểm soát tốc độ nhận data, tránh bị "ngập"
Mono vs Flux
Bài 01 · Ứng dụng

Khi nào nên dùng WebFlux

  • Cần xử lý nhiều request đồng thời
  • IO-bound operationsGọi API bên ngoài, đọc/ghi database
  • Streaming data real-time
3 kịch bản điển hình
Bài 01 · Tổng hợp

Synchronous vs Asynchronous

Synchronous · RestTemplate / FeignClient

  • Đơn giản, dễ hiểu
  • Phù hợp luồng xử lý tuyến tính
  • Thread bị block khi chờ response

Asynchronous · WebFlux / Kafka

  • Phức tạp hơn khi triển khai
  • Hiệu năng cao, không block thread
  • Phù hợp hệ thống phân tán quy mô lớn

Cấu hình WebFlux trong Microservice

Thiết lập dependency, làm quen WebClient và Router Function — hai thành phần cốt lõi khi triển khai reactive service.

Bài 02 · Thiết lập

Dependency & WebClient

  • spring-boot-starter-webfluxDependency bắt buộc để bật reactive stack
  • Thay thế spring-boot-starter-webHai starter này không nên dùng chung trong một service
  • WebClientHTTP client reactive, thay thế RestTemplate — non-blocking, fluent API, dùng builder pattern để tạo instance
pom.xml
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-webflux</artifactId>
</dependency>
Bài 02 · WebClient

Tạo instance & gọi API

// Tạo instance WebClient client = WebClient.create("http://inventory-service"); // Hoặc cấu hình chi tiết hơn WebClient client = WebClient.builder() .baseUrl("http://inventory-service") .build(); // Gọi API — GET trả về 1 đối tượng Mono<Product> product = client.get() .uri("/products/{id}", id) .retrieve() .bodyToMono(Product.class); // Gọi API — GET trả về danh sách (stream) Flux<Product> products = client.get() .uri("/products") .retrieve() .bodyToFlux(Product.class);

Các method HTTP hỗ trợ: .get() / .post() / .put() / .delete(), kết hợp với .uri(path) để chỉ định endpoint.

  • Khai báo route bằng codeKhông dùng annotation như @GetMapping, @PostMapping
  • Phù hợp với functional programmingRoute được compose lại với nhau như các hàm thuần
route → handler (functional)
Bài 02 · Lưu ý

Những điều cần nhớ khi dùng WebFlux

Apache Kafka — Distributed Messaging

Nền tảng streaming phân tán đứng sau giao tiếp bất đồng bộ giữa các service: broker, topic, partition, offset.

Bài 03 · Khái niệm

Apache Kafka là gì?

  • Distributed event streaming platform
  • Thiết kế để xử lý hàng triệu message/giây
  • Lưu trữ message lâu dàiKhông xóa message ngay sau khi được đọc, khác với message queue truyền thống
append-only log
Bài 03 · Khái niệm cốt lõi (1/2)

Broker & Topic

  • BrokerServer Kafka chạy và quản lý message. Nhiều broker hợp thành một cluster, có khả năng chịu lỗi cao (fault-tolerant)
  • TopicKênh logic để phân loại message — giống như hộp thư điện tử theo chủ đề. Ví dụ: order-created, payment-completed
Kafka cluster
Bài 03 · Khái niệm cốt lõi (2/2)

Partition & Offset

  • PartitionMột topic được chia thành nhiều partition; mỗi partition là log tuần tự, không thay đổi — giúp tăng parallelism và throughput
  • OffsetSố thứ tự của mỗi message trong partition. Consumer đọc từ offset nhất định, và có thể đọc lại message cũ
partition · log tuần tự
Bài 03 · Vai trò

Producer

  • Gửi message vào Topic
  • Chọn partition theo keyHoặc theo round-robin nếu không chỉ định key
  • Hỗ trợ batch sendingGộp nhiều message để tăng hiệu suất gửi
producer → partitions (theo key)
Bài 03 · Vai trò

Consumer

  • Đọc message từ Topic
  • Lưu trữ offset đã đọc
  • Có thể đọc lại message từ offset bất kỳ
consumer đọc theo offset
Bài 03 · Scale

Consumer Group

  • Nhóm nhiều consumer cùng đọc 1 topic
  • Mỗi partition chỉ được đọc bởi 1 consumer trong groupĐảm bảo message được xử lý đúng một lần trong group
  • Scale horizontally bằng cách thêm consumer
consumer group
Bài 03 · Kiến trúc

Kiến trúc tổng quan Kafka

Producer ghi vào broker phù hợp trong cluster → Controller quorum (KRaft) theo dõi trạng thái cluster, bầu leader cho từng partition → Consumer (theo consumer group) đọc dữ liệu từ cluster.

Bài 03 · Cách Kafka hoạt động

Replication — Leader & Follower

  • Mỗi partition có 1 leader và N replica (follower)Các replica được đặt trên các broker khác nhau để chịu lỗi
  • Producer & consumer chỉ làm việc với leaderFollower chỉ âm thầm đồng bộ dữ liệu từ leader
  • Leader gặp sự cố → bầu lại leader mớiMột follower đang đồng bộ đầy đủ (trong ISR) sẽ được chọn thay thế
Partition P0 — leader & follower
Bài 03 · Cách Kafka hoạt động

In-Sync Replicas & độ bền dữ liệu

  • In-Sync Replicas (ISR)Tập hợp các replica đang đồng bộ đầy đủ, sẵn sàng thay leader khi cần
  • acks=0Producer không chờ xác nhận — nhanh nhất, dễ mất dữ liệu nhất
  • acks=1Chờ leader ghi xong rồi mới xác nhận — cân bằng tốc độ và an toàn
  • acks=all (-1)Chờ toàn bộ ISR xác nhận — an toàn nhất, độ trễ cao hơn
tốc độ vs độ an toàn
Bài 03 · Cách Kafka hoạt động

Lưu trữ & Retention

  • Segment fileMessage trong mỗi partition được ghi tuần tự thành các segment file trên đĩa
  • retention.ms / retention.bytesMessage tự động bị xoá sau một khoảng thời gian hoặc khi vượt dung lượng cấu hình — không phải ngay sau khi được đọc
  • Log compactionGiữ lại bản ghi mới nhất theo từng key, phù hợp lưu trạng thái thay vì sự kiện
retention · log compaction
Bài 03 · Luồng hoạt động

Từ Produce đến Consume

Producer gửi record → leader append vào log → follower đồng bộ → khi đủ số ISR xác nhận theo acks, leader phản hồi thành công → consumer poll() lấy batch mới → xử lý xong rồi commit offset.

Bài 04

Event-Driven Architecture

Khi Kafka trở thành xương sống giao tiếp: các service phát và lắng nghe sự kiện thay vì gọi trực tiếp lẫn nhau.

Bài 04 · Khái niệm

Kiến trúc hướng sự kiện (EDA)

  • Service giao tiếp qua việc phát và lắng nghe Event
  • Event là gìĐiều gì đó đã xảy ra — ví dụ: Order Created, Payment Done
1 event, nhiều nơi lắng nghe
Bài 04 · Thành phần

Event Producer · Broker · Consumer

  • Event ProducerPhát ra event khi có thay đổi trạng thái, không biết ai sẽ lắng nghe. Ví dụ: Order Service phát OrderCreatedEvent
  • Event BrokerTrung gian nhận và phân phối event, đảm bảo event không bị mất — Apache Kafka đảm nhiệm vai trò này
  • Event ConsumerLắng nghe và xử lý event quan tâm, độc lập với producer. Ví dụ: Inventory Service lắng nghe OrderCreatedEvent
Bài 04 · Ưu điểm (1/2)

Loose Coupling — Liên kết lỏng

  • Producer không biết consumer
  • Dễ thêm consumer mớiKhông cần sửa lại producer khi thêm một consumer mới
  • Giảm phụ thuộc giữa các service
thêm consumer không đụng producer
Bài 04 · Ưu điểm (2/2)

Hiệu năng & Fault Tolerance

  • Tăng hiệu năngProducer không chờ consumer xử lý xong; consumer xử lý theo khả năng riêng; tự nhiên hỗ trợ scale
  • Fault ToleranceMessage được lưu trong Kafka — consumer down thì message không mất; khi khôi phục, consumer đọc tiếp từ offset đã lưu
consumer down → khôi phục
Bài 04 · Đánh đổi

Nhược điểm

  • Khó debug hơnLuồng xử lý không còn tuyến tính như gọi hàm trực tiếp
  • Eventual ConsistencyDữ liệu không nhất quán ngay tức thì giữa các service
  • Cần thiết kế Event Schema cẩn thận
eventual consistency

Bài 05

Cấu hình Kafka trong Spring Boot

Từ dependency đến code thực tế: KafkaTemplate để gửi, @KafkaListener để nhận, và cách xử lý lỗi.

Bài 05 · Thiết lập

Dependency & application.yml

// pom.xml <dependency> <groupId>org.springframework.kafka</groupId> <artifactId>spring-kafka</artifactId> </dependency> # application.yml spring: kafka: bootstrap-servers: localhost:9092 consumer: group-id: inventory-service auto-offset-reset: earliest # hoặc latest

spring-kafka được thêm vào mọi service cần dùng Kafka. auto-offset-reset quyết định consumer mới sẽ đọc từ đâu khi chưa có offset đã lưu.

Bài 05 · Producer

KafkaTemplate

@Service public class OrderEventPublisher { @Autowired private KafkaTemplate<String, Object> kafkaTemplate; public void publish(OrderCreatedEvent event) { kafkaTemplate.send("order.created", event); } }

Inject KafkaTemplate<String, Object>, gọi kafkaTemplate.send(topicName, message). Hỗ trợ gửi bất đồng bộ với CompletableFuture.

Bài 05 · Consumer

@KafkaListener

@Service public class InventoryEventListener { @KafkaListener(topics = "order.created", groupId = "inventory-service") public void onOrderCreated(OrderCreatedEvent event) { // trừ tồn kho theo event inventoryService.decreaseStock(event); } }

Annotation gắn trên method để lắng nghe topic. topics: danh sách topic cần lắng nghe · groupId: consumer group.

Bài 05 · Serialization

Serialization / Deserialization

  • ProducerJsonSerializer để chuyển Object → JSON trước khi gửi vào Kafka
  • ConsumerJsonDeserializer để chuyển JSON → Object khi nhận
  • Cấu hìnhvalue-serializer và value-deserializer trong application.yml
Object ⇄ JSON
Bài 05 · Xử lý lỗi

Xử lý lỗi khi consume message

  • DefaultErrorHandlerRetry lại việc xử lý message với delay
  • DeadLetterPublishingRecovererGửi message lỗi vào dead-letter topic để xử lý riêng
  • SeekToCurrentErrorHandlerĐọc lại message lỗi từ đúng vị trí offset
retry → dead-letter
